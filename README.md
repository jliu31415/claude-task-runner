# claude-task-runner

Hand a coding task to Claude Code running in GitHub Actions, together with an exact snapshot of
your local working tree, and get the result back as a pull request.

```bash
submit-task init                       # once per repo: scaffold .claude-task/ and the workflow
submit-task add-feature                # runs .claude-task/tasks/add-feature.md
submit-task docs/spec.md my-feature    # any Markdown file in the repo, explicit task name
submit-task status <task-id>           # the workflow run and its PR
submit-task logs <task-id>             # full run log
```

## What a repo carries

```
.claude-task/
  validate.sh   required  the project's builds/tests; a non-zero exit blocks the PR
  setup.sh      optional  installs toolchains and dependencies on a fresh ubuntu-24.04 runner
  config        optional  KEY=value overrides; every key has a default
  tasks/        your prompts (gitignored by .claude-task/.gitignore)
.github/workflows/claude-task.yml   generated by init, pinned to a runner commit
```

`submit-task init` creates everything except `config` (add it only to override a default) and
never overwrites an existing file. The CLI and the workflow look for everything at these fixed
paths, so a repo has nothing else to configure.

Optional `.claude-task/config` keys:

| Key | Default | Meaning |
|---|---|---|
| `BASE_BRANCH` | `main` | Branch you submit from, the workflow runs on and PRs target |
| `RESULT_BRANCH_PREFIX` | `task-` | Result branch is `<prefix><task-name>` |
| `PROTECTED_PATHS` | empty | Extra paths Claude must not change (trailing `/` = directory) |
| `CLAUDE_MAX_BUDGET_USD` | `10` | Passed as `--max-budget-usd` |
| `CLAUDE_MODEL` | Claude Code default | Passed as `--model` |
| `ANTHROPIC_FEDERATION_RULE_ID` | none | Enables [workload identity federation](#workload-identity-federation) |
| `ANTHROPIC_ORGANIZATION_ID` | none | Required with a federation rule |
| `ANTHROPIC_SERVICE_ACCOUNT_ID`, `ANTHROPIC_WORKSPACE_ID` | none | Optional federation settings |
| `SETUP_GH_APP_CLIENT_ID` | none | Mints setup's `GH_TOKEN` from a [GitHub App](#github-app-for-setup) |

`.github/`, `.claude/` and `.claude-task/` are always protected. A task that changes them fails
instead of publishing.

## Setup

1. **Install the CLI** (once per machine). It needs bash, git, `gh` (authenticated with
   `gh auth login`) and GNU or macOS 12.3+ `realpath`/`readlink`.
   ```bash
   git clone https://github.com/jliu31415/claude-task-runner ~/code/claude-task-runner
   ln -s ~/code/claude-task-runner/bin/submit-task ~/.local/bin/submit-task
   ```
2. **In each repo:**
   - Run `submit-task init`.
   - Fill in `.claude-task/validate.sh`; its stub fails on purpose. Fill in `setup.sh` too, or
     delete it.
   - Commit and push to the base branch.

   The scripts run from the repo root of the snapshot checkout. Setup must write only to
   gitignored paths.
3. **Secrets** (Settings → Secrets and variables → Actions):
   - Claude credential, one of:
     - `ANTHROPIC_API_KEY`, billed per use on the Anthropic API;
     - `CLAUDE_CODE_OAUTH_TOKEN`, from `claude setup-token`, which uses a Claude subscription;
     - no secret at all, with [workload identity federation](#workload-identity-federation).
   - Optional `GH_TOKEN` for `setup.sh` (and no other step), for things like private release
     downloads. Either store a token as `SETUP_GH_TOKEN`, or use a
     [GitHub App](#github-app-for-setup) so nothing expires.
   - Optional `SETUP_ENV`, also for `setup.sh` only, for values the project needs at runtime
     (API keys, app secrets). See [Setup environment](#setup-environment).
4. **Repository setting:** Settings → Actions → General → Workflow permissions → enable **"Allow
   GitHub Actions to create and approve pull requests"**. The default token can stay read-only;
   the workflow requests write access for its publish job only.

### Workload identity federation

Instead of storing an Anthropic key, the run job can trade its GitHub OIDC token for a
short-lived Anthropic token. This bills to your Anthropic API organization; it can't use a
Claude subscription.

1. In the Claude Console, open Settings → Workload identity → **Connect workload** → **GitHub
   Actions**. The wizard creates the issuer, a service account and a federation rule. Scope the
   rule to the dispatch on the base branch:
   - `subject_prefix`: `repo:<owner>/<repo>:ref:refs/heads/main`
   - `audience`: `https://api.anthropic.com`
   - `claims`: `{"repository_owner": "<owner>"}`
2. Put the IDs in `.claude-task/config`. They are identifiers, not secrets:
   ```
   ANTHROPIC_FEDERATION_RULE_ID=fdrl_...
   ANTHROPIC_ORGANIZATION_ID=<organization uuid>
   # only if the wizard gave you these / the rule covers several workspaces
   ANTHROPIC_SERVICE_ACCOUNT_ID=svac_...
   ANTHROPIC_WORKSPACE_ID=wrkspc_...
   ```
3. The caller's workflow job needs `id-token: write`. Workflows generated by v1.1.0+ `init`
   already grant it.

While Claude runs, the runner keeps the identity token file fresh in the background, because
GitHub's tokens expire after about 5 minutes. When a rule is configured, any
`ANTHROPIC_API_KEY`/`CLAUDE_CODE_OAUTH_TOKEN` secret is ignored. Denied exchanges show up in the
Console's workload identity history with the reason. See Anthropic's
[GitHub Actions WIF guide](https://platform.claude.com/docs/en/manage-claude/wif-providers/github-actions).

### GitHub App for setup

Instead of a personal access token, setup can get a GitHub App installation token that's created
for each run and revoked when the job ends.

1. Create a GitHub App (Settings → Developer settings → GitHub Apps) with the webhook off and only
   the permissions setup needs, e.g. Repository → Contents: read-only. Install it on the
   repositories setup reads; the token covers every repository of that installation.
2. Generate a private key and store the `.pem` as the `SETUP_GH_APP_KEY` secret.
3. Put the app's client ID (not a secret) in `.claude-task/config`:
   ```
   SETUP_GH_APP_CLIENT_ID=Iv23li...
   ```

The app must be installed on the account that owns the calling repository. When the client ID is
set, `SETUP_GH_TOKEN` is ignored. Workflows generated by v1.2.0+ `init` pass the key through.

### Setup environment

Your local gitignored env files never reach the runner, since the snapshot leaves ignored files
out. To give the project runtime values such as an API key, store them as the `SETUP_ENV` secret,
typically as `KEY=value` lines, and have `setup.sh` write them where the project reads them:

```bash
[[ -z ${SETUP_ENV-} ]] || (umask 077 && printf '%s\n' "$SETUP_ENV" > config/secrets.env)
```

The target must be gitignored. Claude runs afterwards in the same checkout, so it can read
whatever setup writes; put only values you're willing to expose to the task there. Workflows
generated by v1.3.0+ `init` pass the secret through.

**Upgrading the runner:** `git pull` (or check out a release tag) in your runner clone. Then
delete `.github/workflows/claude-task.yml`, rerun `submit-task init` and commit the new pin.

## How it works

1. **Snapshot (local).** `submit-task` builds a commit from your working tree in a throwaway
   index (`GIT_INDEX_FILE` pointing at a temp file). It never runs `add`, `commit`, `stash`,
   `reset` or `checkout` on your real index or checkout. The snapshot includes:
   - staged and unstaged edits, deletions and mode changes
   - symlinks
   - untracked non-ignored files
   - the prompt

   Other ignored files are left out. A prompt from the gitignored `.claude-task/tasks/` is
   included explicitly; ignored prompts anywhere else are rejected. The snapshot's parent is
   your `HEAD`. The tree is built twice and compared, so a file changing mid-snapshot aborts the
   submission instead of being half-captured.
2. **Push + dispatch.** The commit goes to the new branch `agent-snapshots/<task-id>`. The push
   uses a "ref must not exist" lease, so it never overwrites anything. Then `claude-task.yml` is
   dispatched on the base branch.
3. **Run job** (read-only `GITHUB_TOKEN`, no credentials persisted in the checkout):
   - re-validates the inputs and checks that the snapshot branch still points at the submitted SHA
   - reads the prompt from the snapshot commit
   - runs `setup.sh`, which must not dirty the tree
   - runs Claude Code (`claude -p`, `--permission-mode dontAsk` with an explicit tool list,
     project `.claude/` settings not loaded)
   - collects the diff against the snapshot, rejecting protected-path changes and likely secrets
   - runs `validate.sh`, which must not change the collected tree
   - uploads the patch as an artifact

   Any failure stops the run here, and nothing is published.
4. **Publish job** (`contents: write`, `pull-requests: write`; runs no project code): re-applies
   the patch to the snapshot, checks it reproduces the validated tree, re-checks protected paths
   and secrets, and commits it. It then pushes `task-<task-name>` (again "must not exist", so an
   existing branch is never touched) and opens a PR against the base branch. Last, it deletes the
   snapshot branch, but only if that branch still points at the submitted commit. If Claude
   changed nothing, no branch or PR is created and the snapshot branch is deleted.

The runner's scripts are checked out from the exact commit of the reusable workflow the caller
pinned (`job.workflow_repository`/`job.workflow_sha`). `.claude-task/config` comes from the
dispatched commit on the base branch. The hook scripts come from the snapshot, so local edits to
them are what runs, but Claude can't change them.

### What the PR contains

The result branch is the snapshot plus one commit with Claude's changes. If the prompt wasn't
already committed in `HEAD`, that commit also removes it again, so prompts never land in the PR.

Other local changes in the snapshot that aren't on the base branch yet do show up in the PR. Git
can't leave them out, because Claude's work is built on top of them. The last commit alone is
Claude's work. The PR body lists both parts separately, along with the task ID, snapshot SHA, run
link, the prompt and Claude's report. For a PR with only Claude's edits, push your local changes
to the base branch before submitting.

## Recovery

- **Dispatch failed after the push:** the snapshot branch is kept, and `submit-task` prints the
  exact `gh workflow run ...` command to retry, plus a command to delete the branch.
- **The run failed:** the snapshot branch is kept. Re-run the workflow from the Actions page. The
  transcript is uploaded as artifact `claude-task-<id>-transcript`.
- **The result branch already exists:** publish fails without touching it. The patch is in
  artifact `claude-task-<id>`; apply it with `git apply --index changes.patch` on a checkout of
  the snapshot.
- **Leftover snapshot branches:** `git push origin --delete agent-snapshots/<task-id>`.

## Security notes and limitations

- The prompt, the snapshot and anything they pull in are treated as untrusted input. Claude runs
  with the Anthropic credential in its environment, but no GitHub write token. It could still
  read and misuse that credential via Bash; logs mask registered secrets, but that is not a
  guarantee.
- The run job holds `id-token: write`. The runner removes GitHub's OIDC request variables from
  the hooks' and Claude's environment, but processes run as the same user, so a determined
  process could still recover them and request identity tokens. With federation, Claude can
  also read the short-lived Anthropic token. Don't add cloud federation trust (AWS, GCP, ...)
  that matches this workflow's runs.
- Protected paths are enforced after Claude runs, not inside the session. Claude can edit them,
  but the task then fails.
- Claude could edit ignored files such as installed dependencies in a way that makes validation
  pass without that change being in the PR. Review PRs as you would any contributor's. Nothing
  is ever auto-merged.
- The secret check is a filename and pattern heuristic over added or changed files, not a
  complete scanner. Matches are reported by path only.
- Submodules, nested repositories and Git LFS files are rejected rather than half-uploaded.
- Artifacts and logs are as visible as the consuming repository. On a public repo, anyone can
  read them, including Claude's transcript.
- `submit-task` must be run from the base branch. Commits on it that aren't pushed yet go up with
  the snapshot and show up in the PR (the CLI warns).
- The local CLI and the pinned workflow share only the dispatch inputs and the `.claude-task/`
  layout. Keep your runner clone at or near the pinned version.

## Development

`tests/run.sh` covers snapshot semantics, the safety properties above, `init` and every CI phase.
It runs in throwaway repos with mocked `gh` and `claude`, so it never touches a real remote. It
does not exercise GitHub Actions itself; that needs a real run in a configured repo.
